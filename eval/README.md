# golden set 评测流程

目的：把「词库优化」从主观感觉变成**可测量、可回归**的数字。

因为基准是你手机上的 **iOS 原生微软双拼**，所以这套评测回答的是两个问题：

1. 我们的候选排序离原生还差多少？
2. 我们改了词库之后，是变好还是变坏了？

---

## 一、文件

| 文件 | 说明 |
| --- | --- |
| `words.tsv` | 人工筛选的 145 个词（日常/办公/专业术语/中英混输/成语/易混对） |
| `golden_set.tsv` | **生成物**。由 `tools\New-GoldenSet.ps1` 自动填好词、双拼编码、拼音，两个观测列留空 |
| `demo_filled.tsv` | 用**合成数据**填过的示例，只用来演示/自测评分器，**不是真实结果** |

## 二、生成

```powershell
cd tools
.\New-GoldenSet.ps1
```

它会自动解析每个词的双拼编码，解析顺序：

1. 中文词库里有拼音的（`base` / `8105` / `41448` / `ext` / `others`）→ 用转换器算编码
2. 中英混输表 `en_dicts\cn_en_mspy.txt` → **第二列本身就是双拼编码**，直接用
3. 英文表 `en_dicts\en` / `en_ext` → 第二列也是编码
4. 归一化重试（忽略大小写和标点）→ 让 `WiFi密码` 能匹配表里的 `Wi-Fi密码`
5. 按字组合拼音（用 8105 + 41448 的单字读音）→ 覆盖只在 `tencent` 里、而 tencent 表本身没有注音的词
6. 都不行 → 标记为 `GAP`

编码正确性由 `ConvertTo-Mspy.ps1 -SelfTest` 的 **104 条用例**兜底。

### 关于最后那几个 GAP

`CPU占用` / `API文档` / `Git提交` / `bug修复` / `PPT模板` / `Excel表格` / `PDF文件` / `URL链接`
这些词**在任何词表里都不存在**，而且**这不算缺陷**：
原生 iOS 遇到这类中英混排，同样是你先打英文段、再打中文段，不会给你一个整词候选。
所以我保留它们只为记录，评测时可以忽略——`Evaluate-Candidates.ps1` 会自动跳过编码为空的词。

顺带一个有价值的真实发现，**已经修掉了**：`其它`、`帐户`、`向量库` 在 192 万条词库里
**没有词条**（而 `容器` 在 base 里，权重 188560）。已补进 `src\mspy_overrides.dict.yaml`。
其中 `其它`/`帐户` 是异形词，rime-ice 应该是按校对标准故意不收的，我按较低权重加入，
效果是规范词形（其他/账户）仍排第一。

> 注意区分两件不同的事（我第一版工具把它们混了）：
> **「能编出编码」** ≠ **「词库里这个词条」**。
> 一个词可以靠单字造句勉强打出来，但没有词条就永远成不了一等候选。
> 工具现在会把「无词条」单独报出来。

覆盖探测的结果（`eval\coverage_probe.tsv`，114 个常见词）：
[coverage_probe_result.tsv](coverage_probe_result.tsv) 里可以看全部结论。
**0 个不可打字，3 个无词条** —— 词库覆盖整体是扎实的。

## 三、采集观测值（这一步必须在手机上做）

对 `golden_set.tsv` 里每一个有编码的词：

1. 在**原生键盘**（已切到微软双拼）上打出 `code` 列的内容
2. 找到 `word` 列那个词，记下它是**第几个候选**
   - 第 1 个候选 → 填 `1`
   - 第 2 个 → `2`
   - 候选栏上没有 → 填 `0`
3. 同样操作在我们这套 Rime 方案上，填 `our_rank`
4. 没测的**留空**即可，评分器会跳过

> 建议分批做。先把「日常 + 易混」两类的四十来个词测掉，
> 就能看出词频层面的主要差距；专业术语和成语类通常差别很小。

## 四、评分

```powershell
cd tools
.\Evaluate-Candidates.ps1
```

输出三部分：

**1. 总览** —— 两个来源各自的 `n / top-1 命中率 / top-3 命中率 / 平均位次 / 未找到数`

**2. 分类别** —— 按 日常/办公/专业/中英混输/成语/易混 分组，看差距集中在哪一类

**3. 可执行的清单** —— 这是整件事的重点：

```
>>> REWEIGHTING TARGETS (n): we rank these >=2 positions worse
    词  编码  [分类] native #1  ours #5  (+4)
```

**这些词就是词库重排的具体目标，不是猜的。**

## 五、回归（改了词库之后）

把当前填好的文件另存一份，比如 `golden_set_v1.tsv`；改完词库、重新部署、重新采集后：

```powershell
.\Evaluate-Candidates.ps1 -Baseline .\golden_set_v1.tsv
```

它会逐词比较 `our_rank` 的变化，列出改进项和**退化项**；
只要有退化，脚本就以非零退出码结束——可以直接用作「不达标就不发布」的门槛。

## 六、已知边界（说明白，免得误判）

- **需要人工采集。** 我这边没有 librime 运行时，无法自动查询候选。
  采集一次大约十几分钟，做完可以长期复用。
- **位次只在同一候选数下可比。** 我们的 `page_size` 是 5，如果你在原生键盘上
  展开看了更多候选，「未找到」的判定口径会不一致。建议两边都只看首页。
- **`composed-from-chars` 标记的行是多音字风险点。** 那几行的拼音是按单字读音拼的，
  遇到多音字可能不准（比如「还」「得」），填之前先自己念一下确认。
- **权重调整不在这套脚手架里。** 这里只负责「测」和「防退化」；
  具体怎么调权重是 `可行性分析与设计方案.md` §8.2 的三层权重模型。
